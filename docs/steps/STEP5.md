# Step 5: The AXI4-Lite Wrapper

Step 4 gave the accelerator a simple private interface (write port, start, done, read port). Real systems don't wire a CPU to private ports. They use a standard bus. Step 5 puts the accelerator behind **AXI4-Lite**, so a CPU (MicroBlaze, Zynq ARM) or your UART-to-AXI bridge can drive it with ordinary register reads and writes.

This step reuses your AXI4-Lite project: the slave's handshake style comes from `axil_mem_slave.v`, and the testbench uses your `axil_master.v` and `axil_checker.v` unchanged.

## Register map (the "software view")

| Address | Name | Access | Meaning |
| --- | --- | --- | --- |
| 0x000 | CTRL | W | write 1 to bit 0 to start a run (it clears itself) |
| 0x004 | STATUS | R | bit 0 = busy, bit 1 = done |
| 0x008 | CYCLES | R | clocks taken by the last run (11 for 4x4) |
| 0x00C | ID | R | 0x5A000408 = "SA", N=4, 8-bit data. Software reads this first to check it found the right block. |
| 0x400 + 4·(i·N+j) | A[i][j] | W | low byte = signed INT8 |
| 0x800 + 4·(i·N+j) | B[i][j] | W | low byte = signed INT8 |
| 0xC00 + 4·(i·N+j) | C[i][j] | R | signed 32-bit result |

For example, A[1][2] is at 0x400 + 4×(1×4+2) = **0x418**, and C[3][3] is at 0xC00 + 4×15 = **0xC3C**.

What software does for one multiply:
```
write 0x400..0x43C  (16 values of A)
write 0x800..0x83C  (16 values of B)
write 0x000 = 1     (start)
read  0x004 until bit1 = 1   (poll done)
read  0xC00..0xC3C  (16 results)
```

## Error responses

| Situation | Response | Why |
| --- | --- | --- |
| normal access | OKAY | |
| misaligned address (not a multiple of 4) | SLVERR | registers are 32-bit words |
| wrong direction: read A/B, write C/STATUS/CYCLES/ID | SLVERR | the register exists but not for that operation |
| write A, B or CTRL while busy | SLVERR | refusing loudly is better than silently corrupting a run |
| nothing at that address | DECERR | the address decodes to no register |

## Key design decisions

| Decision | Why |
| --- | --- |
| Reuse the `axil_mem_slave` handshake (AW and W latched independently, READY not dependent on VALID) | It is already proven protocol-compliant, and the checker confirms it again here with 0 violations. |
| One element per 32-bit word | Simple and works for any N (up to 16x16 fits each 1 KB region). Packing 4 INT8s per word is an optimization, discussed below. |
| Row and column taken from address bits | No divider in hardware. That is why N must be a power of 2. |
| A busy write gets SLVERR, not a silent ignore | Software can see that its write was refused. In step 4 it was only ignored. |
| CTRL.start is a 1-clock pulse generated by the wrapper | Software writes 1 once; there is no need to write 0 again. |
| ID register | A standard practice: drivers check the ID before using a block. |

The 8x8 version also passes 200 random jobs with 0 protocol violations.

**Bug check:** with the busy check removed, the testbench fails on "write A while busy" and "start while busy".

## The most important number in this step: 249 vs 11

The math takes **11 clocks**, but a whole job over AXI4-Lite takes **249 clocks**. About **95% of the time is spent moving data over the bus**: 32 writes, polling, 16 reads, each a few clocks. This is the classic accelerator lesson: **compute is cheap, data movement is expensive.** Two ways to improve it:
1. **Pack 4 INT8 values into one 32-bit write**, using WSTRB byte lanes. A and B then take 8 writes instead of 32, roughly halving the job time.
2. **Use AXI-Stream or DMA** to stream whole matrices with no per-word handshakes. That is how real accelerators (and NVIDIA's tensor-core data paths) are fed.

Quote this in interviews. It shows you measured the system, not just the compute.

## Run it in Vivado 2022.1

1. Close any open simulation.
2. Add design source: `axil_systolic.v`.
3. Add simulation sources: `tb_axil_systolic.v`, `axil_master.v`, `axil_checker.v`. The master and checker are only used for testing here, so they go in simulation sources.
4. Under Design Sources, set `axil_systolic` as Top. The tree is `axil_systolic` → `u_acc : systolic_top` → `u_core` → skews and array.
5. Under Simulation Sources, set `tb_axil_systolic` as Top.
6. Run Behavioral Simulation. The runtime is already `-all`. This test is about 505 µs.
7. Expect `AXI protocol checker: 0 violations` and `PASS: axil_systolic N=4, 0 errors`.

## In the waveform, look for

Use `restart` then `run 3us`, and add the AXI signals `awvalid awready wvalid wready bvalid bready arvalid arready rvalid rready` plus `dut/u_acc/state`:
- 32 write bursts (AW+W, then B) loading A and B.
- One write to address 0, then `state` going 1 → 2 → 3 → 4.
- Repeated reads of 0x004 (polling) until done.
- 16 reads from 0xC00 to 0xC3C returning C.

## Interview chain on this step

1. *Why AXI4-Lite?* It is the standard control bus on Xilinx and Arm systems. Any CPU or bridge can use the accelerator without custom wiring.
2. *What's your register map?* CTRL, STATUS, CYCLES, ID, then A, B and C regions. An ID register lets software detect the block.
3. *What happens if software writes A while a run is in progress?* The slave returns SLVERR and the data is unchanged. I tested it, including a rerun to prove A was not modified.
4. *How do you know your AXI is correct?* A protocol checker watches every cycle for 6 rules (VALID held until READY, stable payload, response ordering, no X, no EXOKAY), with 0 violations over 200+ jobs.
5. *Where is the bottleneck?* The bus: 249 clocks per job versus 11 for the compute. Fixes: packed writes, AXI-Stream, DMA, or double buffering.
6. *Why must N be a power of 2?* Row and column come straight from address bits, so no divider is needed in hardware.
